## 1. 当前范围

当前实现“已核原生结果/持久Worker → 版本化结果包 → 数据库存储 → 管理员查看与逐份发布 → 普通用户查看本人报告”。沿用Go/Gin、Vue、PostgreSQL和现有认证。

已新增SQLite持久队列、来源revision游标、封口时间、前台调度循环、公司Responses客户端、逐请求回执、结果不明隔离、已核结果复用和产品导出桥接。它们接收显式本地任务catalog；尚未接入原始审计每日增量的生产适配器和自动任务识别。完整周输入仍需解决有界读取，不能把两任务API验证称作完整周评自动链路验收。

不提供排行榜、用户评论、手工改分、规则编辑器、批量审批或页面启动/重试评测按钮。现有“接入记录”只记录结果包导入，不伪装模型执行进度。生产迁移、部署、数据写入和正式员工发布均未执行。

## 5. 存储、调度和恢复

PostgreSQL迁移`backend/migrations/241_zhiyongli_reports.sql`仅在本地执行。zhiyongli_runs记录接入批次；reports记录用户、周期、修订和发布；evidence记录同修订引用。精确邮箱映射现有账户，导入不创建用户；修订唯一、当前发布唯一，短事务和advisory lock避免并发替换。新草稿不立即取代已发布结果。

`tools/zhiyongli/runtime.py`的SQLite WAL队列另存持久任务、游标、来源索引和动作回执。整批索引与游标同事务推进；revision不能倒退或同号改内容。输入或合同变化产生新任务版本，移出最新索引的旧队列不执行。到期才封口，单Worker文件锁禁止并发评分。

- `ingest`摄入明确绑定当前执行合同SHA的catalog，不复制共享原文。
- `tick`默认只做确定性/复用工作；`--company-api`才允许调用公司`https://ai.apsatcom.com/responses`。
- `run --catalog ...`作为显式启动的前台循环，每轮检查索引及到期任务；SIGTERM/SIGINT可停，不注册系统服务、监控或心跳。
- API无HTTP/超时自动重试。发送前写请求SHA，流中保存response_id，终态保存完整原响应。断流/5xx/超时记unknown；旧requesting恢复时只核回执，不自动重发，同目标新版本也被阻断。
- 原生合同有效后为review_pending；`accept --proof`绑定实际结果SHA及前序语义核对范围。它是既有evidence_checked的落盘，不能以结构成功自动填写，也不是新增AI评分层。
- 显式复用已核review需同时绑定unit/review签名和核对声明；真实回执再验通过response_receipt引用，不新增API请求。月依赖全部accepted才汇总，亦可引用已签名覆盖清单做024确定性重算。
- 仅兼容实测`period_reviews[].challenge`错位到`context.challenge`这一项格式错误；保留原响应和逐字段迁移记录，不推断来源枚举、不生成引用、不改分。冲突位置拒绝。

常用命令（路径须替换为实际已核清单）：

```sh
python3 tools/zhiyongli/runtime.py --state <受控队列目录> ingest <当前catalog.json>
python3 tools/zhiyongli/runtime.py --state <受控队列目录> run --catalog <当前catalog.json>
python3 tools/zhiyongli/runtime.py --state <受控队列目录> status
python3 tools/zhiyongli/export_queue.py --state <受控队列目录> --manifest <显式身份映射.json> --output <新结果包.json> --rules-version 1.5
```

不附带`--company-api`不会发模型请求。新请求仅走当前固定合同，不恢复历史iteration_011参数实验。
